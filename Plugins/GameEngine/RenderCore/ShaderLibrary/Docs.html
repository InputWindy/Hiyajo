Private/FShaderParser.h

FShaderParser.h —— .shader 文本的解析与注入（私有）

`ShaderLibrary` 的内部实现头（`Private/`，不对外）。它**不是**通用 HLSL 前端：

* 只认 `#pragma vertex/fragment` 指定的两个入口所引用的那两个 struct；

* 只把 struct 成员按语义表重写成 `layout(location = N) in|out` 的全局量；

* 函数体里只做「实例名.成员名」的定点替换（成员名表来自解析出的 struct 声明）—— **函数体其余部分照 GLSL 写，包括类型名**（struct 成员写 `float3`/`float4`，函数体里写 `vec3`/`vec4`）。

任何不认识的东西（未知语义、未知状态键、缺 pragma、未知类型）都**报错并给出文件:行**。不猜的理由很实际：猜错的典型症状是「颜色对、位置全错」，查它比读一条报错贵得多。

Public/ShaderLibrary.h

ShaderLibrary.h —— Unity 风格 .shader 文本库

这一层只回答一个问题：**给我一个 shader 名，我还原出渲染侧需要的一切**。答案是一个 `FShaderDesc`（两个阶段的 SPIR-V、材质布局、render state），名 = 文件名（`Content/Shaders/<名>.shader`）。

**为什么布局与 GLSL 由同一个解析器一起产出**（design D1）：材质常量块如果「CPU 侧算一遍、GLSL 里再写一遍」，就有一份可以悄悄错位的重复数据 —— 症状是「颜色对、位置全错」这种要查一整天的 bug。所以两者由**同一份 `Properties` 声明序**生成，再用**编译出来的 SPIR-V 反查偏移**做断言（不是重算同一个公式）。

**为什么是插件而不是引擎核的一部分**：引擎核（Core/Engine）零应用假设，`.shader` 语法、glslang、set0/set2 绑定约定都是**渲染侧的应用假设** —— 它们必须能被卸载、能被替换。

**改 shader 需要重启**：本切片不做热重载（design D2 的显式选择）—— `Initialize` 阶段一次性扫描 + 编译 + 缓存，之后只读。

类 FShaderLibrary : FFrameExtension, IPipeline<IInit, IShutdown>

`.shader` 文本库本体 —— **一个引擎侧帧**（只挂 `IInit`/`IShutdown`）。

**安装位置很重要**：它挂的是引擎阶段，所以必须装进驱动这些阶段的收集者，即宿主的子节点（`ExampleEngine.cproject` 的 `Plugins` 数组），而不是 `Render.cplugin` 的 `Plugins` —— 后者是 `FRender` 的渲染阶段收集者，装进去会拿不到节点、`Initialize` 永不执行（`PrimitiveRegistry` 踩过这个坑）。`Render.cplugin` 只需要它的 `PrivateIncludes`，好让渲染侧能 include 这个头。

**线程**：`Initialize` 阶段一次性写完（扫描 + 解析 + 注入 + 编译 + 缓存），之后只读 —— 渲染线程读 `Get()`/`GetDiagnostics()` 安全。

字段

访问域字段说明
privatestd::unordered_map<Name::FName, FShaderDesc> Shaders;按名查询的表（`Get()` 走它）。**索引是 `FName` 而不是 `std::string`**：每帧的 `Get()` 不该做字符串哈希

包含的头文件

头文件功能
Core/Export.h`MAHO_EXPORT` / `MAHO_IMPORT`（引擎核心提供）

宏 MAHO_SHADERLIBRARY_API : MAHO_EXPORT / MAHO_IMPORT（随构建开关切换）

编译本插件时构建系统定义 `MAHO_SHADERLIBRARY_MODULE_EXPORTS` ⇒ `MAHO_EXPORT`；消费方为 `MAHO_IMPORT`。

**为什么必须有**：`FShaderLibrary` 与 `FShaderDesc` 都要跨 DLL 边界 —— 渲染侧拿到的是指针、且实例由本模块构造并销毁，虚表与删除析构符只能在本模块生成。少了这个标签，消费方会各自生成一份 vftable，卸载后 `delete` 静默崩（0xC0000005）而不是编译错。
