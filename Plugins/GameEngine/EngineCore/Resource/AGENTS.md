# Resource - Agent Entry

All AI agents must read this file before entering this plugin.

## Design Constraints (strict)

- Responsibility boundary: async resource import/export. New resource type = specialize `TResourceImporter/Exporter<T>` (pure codec, sees bytes not threads) + `TResourceCreator<T>` (instance factory, defined out-of-line in the type's own module); host owns the lifecycle: `Initialize` starts the IO thread, `Tick` every frame, `Shutdown` stops the thread and clears the catalog.
- **Never construct a resource in a header template.** `Import<T>` / `CreateResource<T>` go through `TResourceCreator<T>` so the instance's vtable + deleting dtor live in the resource type's module, never in the caller's: a caller may be a sub-plugin that is unloaded while the resource is still cataloged, and the engine's Shutdown then deletes it through a vptr into a freed image (validated crash: `FContentBrowser.dll` unloaded before `FResourceSystem::Shutdown`).
- **Resource types are DLL interfaces** (the compile-time half of the same rule). `FResource` is `MAHO_RESOURCE_API`, every concrete asset type is `MAHO_ASSET_API`, so consumers resolve the vtable + deleting dtor through the import table and *cannot* emit a local copy - the compiler fails instead of stamping a dying module's vptr into an instance. A project-side resource type must be exported the same way (keep its vtable in a module that outlives the catalog); for an unexported type only the `TResourceCreator<T>` factory protects it.
- **Creator releases, in its own teardown.** `CreateResource<T>` / `Import<T>` leaves an entry in the catalog that OUTLIVES the caller: `FResourceSystem::Shutdown` clears it only after every shutdown stage ran, while a sub-plugin unloads *during its parent's shutdown* - so a leftover is destroyed after its owner's module is already gone (its dtor / mirror release lands in a freed image). Release with `DestroyResource` in your own teardown stage: `IPreUnInstall` for a render feature (driven by `FRender`, see `Render.cpp`), `IShutdown`/`IPreUnInstall` for a layer. Validated: `FScene` (a Render sub-plugin) created `SceneColor`/`SceneDepth` with no teardown stage at all - the catalog then destroyed them with `FScene.dll` unloaded (intermittent `0xC0000005` on close).
- **Leftovers are reported, never swallowed.** `FResourceSystem::Shutdown` lists every catalog entry and pending transfer it is about to destroy, so a violated contract is loud instead of a silent cross-module dtor (that report named `SceneColor`/`SceneDepth`). Keep it, and keep its own reads module-safe: print `FName::GetId()` (the Name pool may already be shut down - `ToString()` would read freed pool storage) and `FResource::GetPath()` (a NON-virtual getter; `typeid(*Resource)` dereferences the vptr, the very thing dangling when the owner unloaded first).
- **Known gap**: a pending `Import<T>` keeps its continuation (`OnBulkReady` - a closure created in the CALLER's TU, because `Import<T>` is a header template) inside the system until the transfer completes; a caller unloaded with a transfer still in flight leaves that closure to be destroyed later. Until a cancel/ownership API exists, "never unload with transfers in flight" is part of the contract (the leftover report covers it).
- Dependencies go only through `.cplugin` `Dependencies` (`["Name", "Paths"]`), include `<Resource.h>`, no cross-directory relative includes.
- Implementation notes:
  - `TSingleton` + `FThreadedServer`, `Get()` defined in `Private/Resource.cpp` (process-unique inside Resource.dll).
  - **Import**: IO thread reads file -> game thread decodes in `Tick` (Importer called on game thread, safe to touch catalog/state).
  - **Export**: caller thread encodes (Exporter reads catalog resources synchronously, no cross-thread sharing) -> IO thread writes to disk -> `OnDone` returns to game thread via `Tick`; caller must keep the resource alive and unchanged until completion.
  - Transfer details (`FTransferState` / `FBulkData` / `FTransferHandle`) all inside the cpp, header only forward-declares.
