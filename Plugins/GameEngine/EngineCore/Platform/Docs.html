Platform.h —— 原生表面 + 输入事件

平台层只提供两样东西：**原生表面**（给 RHI）与**原始输入**（给输入事件经纪 / ImGui 驱动）。「窗口」这个概念被收进单一访问函数 `IPlatform::GetNativeWindow()` 里 —— 因为不是每个平台都有窗口（无头、Android surface、iOS view），把窗口语义藏在一个访问器背后，上层就不必到处写 `if (headless)`。

线程模型（硬约束）：`FPlatform` 继承 `FThreadedServer`，窗口的创建与消息泵都在它自己那根常驻线程上。理由是 Win32 的窗口消息队列属于创建窗口的那根线程 —— `PeekMessage` 只看调用线程自己的队列，而键盘 / 字符 / 滚轮只以消息形式存在（鼠标能幸免，是因为位置与按钮还有全局查询可读）。此前窗口由「恰好抢到 IInit 的那个 worker」创建，而泵每帧被派发到另一根 worker：24 根里 23 帧在问错的队列，于是按键以约 2 条/秒 到达、延迟 0.2–2 秒并成批涌出（「鼠标正常、键盘一股脑一串」）。帧侧只允许读 `CachedSurface` / `CachedWidth,Height` / `bCachedShouldClose` / `CachedToolkitWindow` 这几个缓存（由 `PublishWindowState` 在平台线程刷新）；任何 GLFW / Win32 窗口调用都必须经 `RunOnPlatformThread`。附注：`ImmDisableIME` 同样是 thread-scoped，所以它也在同一根线程、任何窗口存在之前（`OnInitialize`）调用。

输入的模型是：每帧发布一个带帧号的帧（`FInputFrame` = 帧号 + 快照 + 该次泵里的边沿事件），消费者各自持游标按帧号读取 —— 恰好一次、按序。快照（鼠标位置/按钮、键盘按下状态、修饰键、焦点）本身仍是可重复读的；边沿 / 字符 / 滚轮是瞬时的，所以随那一帧一起发布；滚轮不再「交换清零」，因此编辑器上下文与游戏上下文都能读到同一份增量，不再有单消费者约束。旧设计是「一个可排空的事件流、谁先排空谁拿走」，那正是「错过携带按键抬起的帧 ⇒ ImGui 认为键一直按着 ⇒ 自动重复」的成因。

引擎 core 完全不认识 ImGui / GLFW 类型：键码就是稳定的整数（GLFW 键码），由 UI 层自行映射 —— 这样平台层不会因为某个 UI 后端而长出一条依赖。

结构体 MInputEvent

单条原始输入事件，与对应 GLFW 回调的负载**逐字段对齐**。做成无 union 的扁平记录：union 让「哪个字段有效」依赖外部约定且容易读错，而这里多出的几个 int / float 相对一次事件泵的开销可以忽略 —— 换取的是读代码时不需要查表。与该 Type 无关的字段保持默认值。

结构体 MInputContext

平台与 UI 功能之间的**中立输入快照**。写者是 Platform（它的 GLFW 回调在窗口循环线程里跑），读者是 UI 功能（渲染线程），所以它按「可重复读的状态快照」设计：任何读者拿到同一份值，什么都不消费 —— 这使多个消费者可以各自独立地读，而不需要谁先谁后的约定。

滚轮也不会被「清掉」：它在一次泵里累积，随那一帧发布，所有读到该帧的消费者拿到同一份增量。边沿 / 字符 / 焦点同样不属于快照 —— 它们是瞬时的，随那一帧的 `Events` 一起走（见 `FInputFrame`）。

类 IPlatform

平台层向后端暴露的**最小**接口：只有原生表面。把它保持这么小是刻意的 —— 每多一个虚函数，就把更多平台概念固化进上层；而 RHI 真正需要的只有「表面句柄」这一件事，其余（尺寸、事件、关闭请求）都由具体实现类直接提供，不经这层抽象。

publicvirtual ~IPlatform() = default虚析构：实现类（GLFW / EGL 后端）在 cpp 的匿名命名空间里，必须能通过基类指针正确销毁

类 FPlatform : FFrameExtension + IPipeline<IPreInit, IInit, IPostInit, IBeginFrame, ITick, IEndFrame, IExit, IPreShutdown, IShutdown, IPostShutdown>

平台系统（一个引擎帧）：原生表面 + 事件。**它挂在完整阶段序列上**，因为引擎循环正是通过它推进的：`Tick` → 泵事件 + `ShouldClose` → 请求引擎退出；`BeginFrame`/`EndFrame` 则把「泵事件」放在帧的两端，让输入在整帧内保持稳定。

后端是**惰性创建**的：`Initialize` 不做任何事，`CreateWindow` / `CreateHeadlessContext` 才按平台选后端（GLFW 或 EGL pbuffer），`DestroyWindow` 可以随时切回无头 —— 于是「无表面」是一个正常状态而不是错误状态，这也解释了 `GetNativeWindow()` 为什么会返回 `nullptr`。

三个 `std::function` 钩子（事件泵 / 关闭查询 / 工具包窗口）是后端差异在头里的全部残留：具体后端类型（`FGlfwWindow` / `FEGLHeadlessWindow`）只活在 cpp 的匿名命名空间里。
