Text.h —— 本地化文本（句柄 + 目录，服务层）

本地化的两条腿：`FText` 是**句柄**（`{Namespace, Key, Source}`），`FTextManager` 是**目录 + 当前语言**（`SetCulture` 选语言，`FText::Resolve()` 查翻译并回退到原文）。

**为什么用句柄而不是直接存翻译后的字符串**：界面在第一帧构建时就持有文本，而玩家可能在第 300 帧切语言。句柄只记「哪个命名空间的哪个键」，切语言后**下一次 `Resolve()` 自然给出新文本** —— 不需要重建任何 UI 组件。

**为什么要 `Source`（原文）**：翻译缺失是常态（新加的文案还没来得及翻）。把原文随句柄一起带着，`Resolve` 就能优雅回退：宁可显示英文，也不要显示一个键名。

**为什么 `Namespace` 而不是纯 Key**：`Key` 会在不同系统间撞名（例如都叫 `Title`），命名空间把「哪个模块的 Title」这件事显式化，也让翻译文件可以按模块拆分。

**线程安全**：目录由互斥量保护（`Resolve` 很可能来自渲染线程，而 `AddTranslation` 可能来自加载线程）。

类 FText

本地化文本**句柄**：只存 `{命名空间, 键, 原文}`，不含翻译结果。

**为什么它是可拷贝的值类型**：UI 树、组件、配置里到处要存文本，如果句柄是指针 / 引用，文本的生命周期就会变成所有人的负担；值语义让「持有文本」这件事零心智能负担（代价是三个字符串的拷贝，而它们通常很短且在 UI 构建期只拷一次）。

**相等性只比 `{命名空间, 键}`**（不比原文）：同一句话换了个原文写法仍应视为同一个文本 —— 这对「按文本键去重 / 做 diff」很有用。

类 FTextManager : FFrameExtension, IPipeline<IInit, IShutdown>

本地化管理器 —— **一个帧**（挂 6 个 stage）：`Initialize` 里发布全局访问点并定下默认语言，`Shutdown` 里撤销。语言目录是运行期可变状态，交给有依赖排序的帧持有，「谁在谁之前设语言」才有确定性。

**为什么默认语言是 `en-US`**：`CurrentCulture` 有初始值，因此**在任何语言被设置之前** `Resolve()` 也是安全的 —— 它只会回退到原文，而不是未定义行为。

**为什么查找要按 `(命名空间, 键, 语言)` 三元组**：目录键实际是把三者拼成一个字符串，这与「一个 FText 只能属于一个语言」的表达能力一致，也避免了嵌套容器。

publicvoid LoadTranslationsFromJson(std::string_view JsonText)从 JSON 数组批量装载翻译，形如：
`[{"Namespace": "...", "Key": "...", "Culture": "...", "Text": "..."}, ...]`
**为什么是 JSON**：翻译要能被非程序员编辑，且要能从构建流程 / 外部工具生成；JSON 是这类「人写、机器读」场景最省事的选择（解析走引擎固定的 Json 依赖）

TextApi.h —— 模块导出标签

本模块的 DLL 导出标签。独立成头：只要「文本管理器访问器」声明的模块不必引入 `Text.h`。

包含的头文件

头文件功能
Core/Export.h`MAHO_EXPORT` / `MAHO_IMPORT`（引擎核心提供）

宏 MAHO_TEXT_API : MAHO_EXPORT / MAHO_IMPORT（随构建开关切换）

编译 `Text.dll` 时构建系统定义 `MAHO_TEXT_MODULE_EXPORTS` ⇒ `MAHO_EXPORT`；消费方为 `MAHO_IMPORT`。

**为什么必须有**：`FTextManager* GetTextManager()` 跨 DLL 返回类型，而管理器（含 `FText`）的虚表与删除析构符必须只在本模块生成 —— `dllimport` 把「消费方各自生成一份」变成编译错误，而不是卸载后 `delete` 时静默崩。
